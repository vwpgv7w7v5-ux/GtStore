# GitHub → Timeweb: обновление сайта

Исходный код находится в `vwpgv7w7v5-ux/GtStore`. Изменения делаются в ветках и
попадают в `main` через Pull Request. Сервер запускает проверенную версию кода;
товары, заказы, фотографии и секреты хранятся отдельно на сервере.

## Что делает GitHub Actions

Workflow `.github/workflows/ci-deploy.yml` проверяет Pull Request, ветки `codex/**`
и `main`: устанавливает зависимости из lockfile, выполняет проверку типов,
проверки старого ядра, тесты v6, импорта/фото и сценариев развёртывания.

После успешных проверок `main` отправляет архив точного проверенного коммита на
Timeweb по SSH. В архиве нет рабочей базы, загрузок, `.env`, `.git` или зависимостей.
Скрипт сервера устанавливает зависимости из lockfile и делает резервную копию данных.
Затем он переключает ссылку на новый релиз, перезапускает API и проверяет HTTP health,
включая SHA коммита. При неудаче возвращается предыдущий код. База и фотографии
автоматически назад не откатываются, чтобы не потерять новые заказы.

PR и ветки `codex/**` никогда не обновляют рабочий сайт. Ручной запуск workflow для
`main` повторяет тесты и развёртывание; устаревший SHA пропускается. Для отката уже
успешного изменения создайте `git revert` через GitHub и пропустите его через проверки.

## Где что хранится

| Содержимое | Размещение |
| --- | --- |
| Код и конфигурация развёртывания | GitHub |
| Неизменяемые релизы | `/srv/gtstore/releases/<sha>` |
| Текущий релиз | `/srv/gtstore/current` — ссылка на релиз |
| База v6 | `/var/lib/gtstore/v6.json` |
| Фотографии и кеш источников | `/var/lib/gtstore/media` |
| Статусы фоновых импортов | `/var/lib/gtstore/import-jobs` |
| Рабочие секреты | `/etc/gtstore/gtstore.env` |
| Резервные копии данных и настроек | `/srv/gtstore/backups` |

Резервные копии и старые релизы автоматически не удаляются. Следите за свободным
местом и настройте хранение копий вне VPS. Файл `data/db.json` в старом коде —
демо-данные legacy-версии; он не используется как production-база v6.

## Однократное подключение существующего сервера

### Обновление подтверждённой установки в `/opt/gtstore`

В консоли Timeweb подтверждены рабочая папка `/opt/gtstore` и три сервиса:
`gtstore-api.service` (4000), `gtstore-admin.service` (4173),
`gtstore-storefront.service` (4174). Для установки исправления без переноса
данных и изменения Nginx предусмотрен отдельный установщик:

```bash
python3 deploy/update-existing.py
```

Он скачивает точный коммит исправления `e85daa017553c962919606c97bbb0bb315b200f9`
из GitHub. Зависимости и загрузка модулей/Sharp проверяются до остановки сайта.
Установщик проверяет принадлежность процессов указанным сервисам, рабочую базу
и HTTPS-адрес сайта. Перед заменой кода он останавливает три сервиса и сохраняет
закрытую резервную копию в `/opt/gtstore-backups/`.

Меняются только исходники v6, скрипт статической выдачи, `package.json`, lockfile
и зависимости. Рабочие `.env`, Git, база, фото, кеш источников, unit-файлы,
секреты и настройки Nginx сохраняются. Затем проверяются API с
`backgroundImport=true` и точное содержимое админки/витрины через локальный
Nginx с настоящим HTTPS-именем и проверкой сертификата. При неудаче возвращаются
прежние код и зависимости; база и фотографии назад не откатываются.

Успех обозначается строкой `UPDATED: <sha>`. Код фиксируется также в
`/opt/gtstore/.gtstore-source-commit`. Сам установщик Excel не импортирует;
после установки требуется полный импорт файла и проверка фото на сайте.
Этот способ обновления берёт исходники из GitHub, но не активирует GitHub Actions.
Включение автоматического deploy и перенос на управляемые релизы описаны ниже.

### Переход на управляемые релизы

Эта инструкция не означает, что сервер уже переключён на новый способ обновления.
Новый управляемый код располагается в `/srv/gtstore`, чтобы сохранить исходную
установку `/opt/gtstore` из присланного архива. Пути старой установки сначала
нужно подтвердить на самом VPS.
Для существующего сайта сначала определите его рабочий каталог, процесс запуска,
файл базы, каталог фото и существующие секреты. Подготовьте резервную копию. Не
создавайте пустую базу вместо рабочей и не меняйте ключи шифрования при переносе.

Нужны системный Node.js 24, Python 3.10+, npm, curl, tar, flock, systemd и работающий
Nginx. Node.js должен быть доступен системному сервису, а не только root через nvm.
Системные зависимости и сертификат HTTPS ставятся отдельно от релизов приложения.

Из проверенного checkout на VPS выполните:

```bash
bash deploy/setup.sh
```

Скрипт создаёт управляемые каталоги и пользователя `gtstore`, устанавливает unit
`gtstore.service`. Он не запускает сервис и не заменяет действующий Nginx.
Существующие неуправляемые пути или отличающийся unit требуют отдельного разбора.

После остановки старого приложения для согласованной копии перенесите его базу в
`/var/lib/gtstore/v6.json`, а фото вместе с `.import-cache` — в
`/var/lib/gtstore/media`. Сохраните исходные данные и настройки для возврата к старому
сайту. Передайте владение рабочими данными пользователю `gtstore`.

Создайте `/etc/gtstore/gtstore.env` по образцу `deploy/gtstore.env.example`, подставив
существующие рабочие секреты. Файл хранится только на сервере, с правами `600`,
владелец root. Пути данных заданы явно; не помещайте этот файл в GitHub.
Существующий процесс, использующий порт 4000, нужно корректно остановить при переходе:
скрипт откажется занимать порт другого приложения.

## Подключение GitHub Actions к SSH

В репозитории откройте **Settings → Secrets and variables → Actions**.

Секреты:

- `DEPLOY_SSH_KEY` — закрытая часть ключа, публичная часть которого добавлена root
  на сервере. Для созданного в этой среде ключа закрытая часть хранится вне репозитория:
  `/workspace/.gtstore-env/ssh/timeweb-cYtKqZ/id_ed25519`. Вносите её через защищённое
  поле GitHub, не через код, issues или сообщения.
- `DEPLOY_KNOWN_HOSTS` — проверенные публичные ключи **самого сервера**, а не ключ
  пользователя. Их можно получить из доверенной консоли Timeweb:

```bash
for file in /etc/ssh/ssh_host_*_key.pub; do
  printf '72.56.28.133 '
  cat "$file"
done
```

Вывод предназначен для `DEPLOY_KNOWN_HOSTS` при стандартном порте 22. При другом
порте запись имеет вид `[72.56.28.133]:порт ssh-ed25519 ...`. Workflow проверяет
подлинность сервера и не принимает неизвестные host keys автоматически.

Необязательные Repository variables (значения по умолчанию):

- `DEPLOY_HOST=72.56.28.133`
- `DEPLOY_USER=root`
- `DEPLOY_PORT=22`

Текущий сценарий установки рассчитан на root для переключения systemd и файлов
релиза; само приложение работает как `gtstore`. Пользователей с правом менять
production-ветку и workflow следует считать имеющими доступ к развёртыванию.
Проверьте доступность SSH из GitHub Actions, включая правила сети Timeweb.

## Первое развёртывание и последующие изменения

До подготовки сервера deploy выключен: проверки кода выполняются, рабочий сайт не меняется.
После подготовки VPS и секретов добавьте Repository variable `DEPLOY_ENABLED=true`.
Затем объедините Pull Request в `main` либо запустите workflow вручную для текущего `main`.
В **Actions → Test and deploy GtStore** дождитесь завершения тестов и deploy.
У первой версии нет предыдущего управляемого релиза: автоматический возврат к
старому способу запуска ещё невозможен, поэтому сохраните старую конфигурацию.

Добавьте маршруты из `deploy/nginx-gtstore.conf.example` в существующий HTTPS-блок
сайта, сохранив сертификат. После `nginx -t` перезагрузите конфигурацию Nginx.
Проверьте API `/api/v6/health`, админку `/admin/`, вход, публичную витрину с реальным
slug магазина, создание заказа и выдачу сохранённых фотографий. В health поле
`commit` должно совпадать с SHA успешного deploy в Actions.
Когда всё проверено, `systemctl enable gtstore.service` включает запуск после reboot.

Дальнейший процесс: изменить код в GitHub → Pull Request → успешные тесты → merge
в `main` → автоматическое обновление сайта. Товары и фото меняются через админку
и остаются на VPS независимо от обновлений кода.

## Текущее ограничение этой облачной среды

Git по HTTPS доступен, но проверка SSH остановилась на недоступном TCP-прокси этой
среды. GitHub API также отклонялся её сетевым прокси. Включение API-домена в черновик
настроек не применяет доступ автоматически. Это не доказывает проблему сервера или
неверный SSH-ключ. Однократную подготовку можно выполнить через консоль Timeweb;
дальнейшие deploy идут из GitHub Actions и не зависят от SSH-доступа из Codex.
